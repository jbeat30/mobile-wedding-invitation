# General JS/TS Coding Conventions (Base)

본 문서는 JavaScript 및 TypeScript 프로젝트의 일관성과 유지보수성, 그리고 개발자 경험(DX)을 극대화하기 위한 범용 코딩 가이드라인입니다.

## 1. 개발 철학 (Philosophy)
- **DX(Developer Experience) 우선**: 코드는 컴퓨터가 읽는 것보다 사람이 읽는 시간이 훨씬 길다. 가독성이 곧 유지보수의 성능이다.
- **실용적 추상화 (Pragmatic Abstraction)**:
  - "나중에 쓰일지도 모르는 코드"를 위해 미리 분리하지 않는다.
  - 실제로 2회 이상 중복되거나, 코드의 복잡도가 한 파일 내에서 감당하기 어려울 때만 추상화/분리를 검토한다.
  - 과도한 분리로 인해 코드 추적(Traceability)이 어려워진다면 단일 파일 내 유지를 선호한다.
- **의도의 명확화**: 주석 없이 코드만으로도 "왜 이 로직이 필요한지" 읽히는 수준을 지향한다.

## 2. 네이밍 규칙 (Naming)
- **PascalCase**: 클래스(Class), 타입(Type), 인터페이스(Interface), UI 컴포넌트
- **camelCase**: 변수(Variable), 함수(Function), 메서드(Method), 객체 속성(Property)
- **snake_case**: 외부 API 통신 데이터 필드, DB 스키마와 직접 매핑되는 필드
  - 내부 로직은 카멜케이스를 쓰되, 외부 데이터 규격은 원형을 보존하여 매핑 혼선을 방지한다.
- **Boolean 변수**: `is`, `has`, `can`, `should` 등의 접두사를 사용하여 상태를 명확히 표현한다.

## 3. 코드 작성 스타일 (Code Style)

### 3.1 변수 선언
- **const 지향**: 모든 변수는 `const` 선언을 기본으로 하며, 반드시 재할당이 필요한 경우에만 `let`을 사용한다. `var`는 절대 사용하지 않는다.
- **구체적 명명**: `data`, `item`, `list`와 같은 모호한 이름 대신 `userInfo`, `messageItem`, `activeUserList` 등 구체적인 명사를 사용한다.

### 3.2 함수 및 로직
- **Early Return**: 조건이 맞지 않는 경우 즉시 반환하여 `if-else` 중첩(Nesting)을 최소화하고 로직의 가독성을 높인다.
- **단일 책임(SRP)**: 함수는 하나의 명확한 행위를 수행하도록 하되, 가독성을 해칠 정도로 무리하게 쪼개지 않는다.
- **화살표 함수**: 단순 로직이나 콜백에는 화살표 함수를 권장하며, 복잡한 로직이나 클래스 메서드는 명시적인 함수 선언을 활용한다.

## 4. 주석 작성 원칙 (Comment Style)
- 모든 주석은 핵심 내용을 빠르게 파악할 수 있도록 **간결한 개조체**를 사용한다.
- 모든 주요 함수와 클래스 상단에 JSDoc을 작성하여 목적과 반환값을 명확히 정의한다.
- `@param`, `@returns`는 간결하게 기술하며, 필요한 경우에만 타입 보충 설명을 추가한다.
- **명사형 종결 어미 사용**: "담당", "반환", "수행", "정의", "검증" 등 명사형으로 문장을 종결하여 가독성 확보.
- **비즈니스 의도 중심**: 기술적 구현(How)보다는 비즈니스 규칙(Why)과 기능의 목적(What)을 설명한다.
- **JSDoc**: 주요 API나 공용 함수 상단에는 JSDoc을 통해 파라미터와 반환값의 의도를 명확히 기술한다.
- **Self-Documenting**: 코드 자체로 설명이 가능한 단순 로직에는 주석을 생략하여 코드의 노이즈를 줄인다.
- 한줄로 작성할 주석은 `//` 으로 한줄 주석을 사용한다.

## 5. 구조 및 추상화 (Architecture)
- **Shared/Utils**: 범용적으로 사용되는 유틸리티는 한곳에 모으되, 프로젝트 도메인 로직이 섞이지 않도록 순수 함수(Pure Function) 형태로 유지한다.
- **Magic Number/String 배제**: 의미를 알 수 없는 숫자나 문자열은 상단에 변수로 선언하거나 상수를 관리하는 별도 파일로 분리한다.
- **의존성 방향**: 하위 레이어에서 상위 레이어를 참조하지 않도록 의존성 방향을 항상 단방향으로 유지한다.

## 6. 실용적 가이드
- 줄 수를 줄이는 기법보다, 코드가 평문(Plain English)처럼 읽히는 것을 더 중요하게 여긴다.
- 코드 리뷰 시 "가장 읽기 편한 구조인가?"를 자문한다.
